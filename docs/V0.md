# v0: lot evaluation against developer policies

v0 is a simple prototype for real estate investment companies.
It evaluates New York City lots and buildings as they stand today, against the policies of three types of developer.
For each site and each developer type, it gives one verdict: Buy, Review or Pass.

v0 serves companies that build new or buy whole properties.
It does not serve people who buy one condo unit or one co-op apartment (decision D2).

v0 is also a harness for testing agents.
Several agents give verdicts on the same sites, with the same tools and the same data.
v0 compares how well each agent judges a site against a policy (D11, D12).

v0 works like a claims department.
In a claims department, a claim comes in and an adjuster checks it against company policy. The decision cites the policy clause that decided it.
Here, a site comes in and the tool checks it against each developer's policy. Each verdict cites its clauses and the evidence.

v0 runs by hand, in notebooks. Nothing runs on a schedule.
It has no model training and no history (D1, D10).

## Words

[`GLOSSARY.md`](GLOSSARY.md) defines every term in this file: the project terms, the property and data terms, and each measure that a policy or a risk factor uses.

## Units

v0 uses US units: feet, square feet, miles, minutes and US dollars (D5).
Walking time uses 3 miles an hour, which is 264 feet a minute.
That is the speed widely reported for Google Maps walking directions. Google does not publish it.
A 15-minute walk is 3,960 feet, or 0.75 miles.

## The sites

Every site comes from PLUTO, which has one row for each tax lot.
Code flags two kinds of lot and leaves them out of every search:

- Condominium lots: building classes that start with R (11,531 lots on 2026-10-30).
- Cooperative buildings: building classes C6, C8, D0 and D4 (7,178 lots on 2026-10-30).

These lots stay in the data, because the neighborhood measures count their homes and floor area.

Sales come from rolling sales. The pull keeps whole lots and buildings only: it leaves out every building class category with "CONDO" or "COOP" in its name.
On 2026-11-13 that kept 44,855 of 82,576 sales.

A sale price is the full price paid for the property, not the change from an earlier price.
A sale under $100,000 is not a market sale. Code flags it and skips it when it looks for a site's last price.
In the 2026-10-30 download, 21,602 of the whole-lot sales were under $100,000. Most of them, 20,108, were $0 transfers.

## How a site gets its verdicts

For each developer type, a site gets one code verdict and one verdict from each agent.
Code does steps 1 and 2. The agents do step 3.

1. **Rules.** Code checks each rule in the policy.
   - If a rule fails, the code verdict is Pass.
   - If a rule has no data, the code verdict is Review.
2. **Risk score.** Code compares the site's risk score with the two limits of the policy.
   - At or below the Buy limit, the code verdict is Buy.
   - At or below the Review limit, the code verdict is Review.
   - Above the Review limit, the code verdict is Pass.
3. **Agent verdicts.** Each agent calls the tools to read the site and the policy. It gives its own verdict and writes a decision letter that cites the clauses and the evidence.
   - No rule limits the agent's verdict. An agent can agree or disagree with the code verdict.
   - Notebook `06` compares the agents.

Code computes every number that a tool returns. The comparison checks each number in a letter against the tool results.

Each verdict names its developer type, for example "Buy, opportunistic policy".
The verdicts use public data and example policies. They are not investment advice.

## The developer types

These numbers are starting values. The code reads them from the policy files: [`example_institutional.yaml`](../profiles/example_institutional.yaml), [`example_standard.yaml`](../profiles/example_standard.yaml) and [`example_opportunistic.yaml`](../profiles/example_opportunistic.yaml). If this table and a file disagree, the file is correct.

| Clause | Safe and institutional | Standard | Opportunistic |
|---|---|---|---|
| Boroughs | Manhattan, Brooklyn | Manhattan, Brooklyn, Queens, the Bronx | All five |
| Price | $10M to $100M | $2M to $25M | Up to $15M |
| Lot area | 10,000 sq ft or more | 2,500 sq ft or more | 1,800 sq ft or more |
| Unused floor area | 30,000 sq ft or more | 8,000 sq ft or more | Any amount |
| Walk to the subway | 8 minutes or less | 12 minutes or less | Any time |
| Deal-breakers | Landmark, flood zone, open vacate order | Landmark | None |
| **Buy** if the risk score is at most | 20 | 40 | 65 |
| **Review** if the risk score is at most | 35 | 60 | 85 |

A deal-breaker is a rule: if the site has it, the verdict is Pass.

## The risk score

Each site has one risk score. All three developer types read the same score. Each type accepts a different amount of risk.
The score is the sum of the points below, with a maximum of 100. The points are starting values. The code reads them from [`risk_factors.yaml`](../profiles/risk_factors.yaml).

| Risk factor | Points | Source |
|---|---|---|
| Open vacate order | 25 | HPD vacate orders |
| Landmark, or inside a historic district | 20 | PLUTO |
| Inside the 2015 FEMA flood zone | 15 | PLUTO |
| Occupied homes on the lot, so tenants must move | 15 | PLUTO |
| Little unused floor area (under 2,500 sq ft), so a new building needs a rezoning | 15 | PLUTO |
| Environmental restriction (E-designation) | 10 | PLUTO |
| No market sale in the last 12 months, so the price is the city's estimate | 10 | Rolling sales, property valuation |
| Price per square foot above the median for the neighborhood | 10 | Rolling sales |
| A walk of more than 15 minutes to the subway | 10 | OpenStreetMap, MTA |

## The price

The price of a site comes from the first of these that exists:

1. The asking price, if you enter one.
2. The last market sale in the last 12 months.
3. The city's market value for the lot.

## The sources

Each source is one of three kinds:

- A **register** describes things as they are now. v0 keeps the newest release.
- An **event log** records things that happened on a date. v0 keeps the open items and everything since the start date in `config.py`, 2025-01-01.
- A **reference** is a code list or a boundary. v0 keeps the newest release.

v0 uses five core sources and five context sources.

| Kind | Source | Portal and id | Keeps | What it gives | In `sources.py` |
|---|---|---|---|---|---|
| Core | PLUTO | NYC `64uk-42ks` | Register: every lot | Lot, building, zoning, maximum FAR, unused floor area, landmark status, flood flags, transit zone | Yes |
| Core | Rolling sales | NYC `usep-8jbt` | Event log: the last 12 months, whole lots and buildings only | The last sale price, and comparable sales | Yes |
| Core | DOF property valuation | NYC `8y4t-faws` | Register: the newest tax year and period | The city's market value for every lot | No |
| Core | DOB NOW job filings | NYC `w9ak-ipjd` | Event log: new buildings, full demolitions and major rebuilds filed since the start date | Building activity on the lot or near it | Yes |
| Core | HPD vacate orders | NYC `tb8q-a3ar` | Event log: open orders, with no rescind date | Open vacate orders | Yes |
| Context | OpenStreetMap walking network | `osmnx` | Register | Walking minutes from each lot | No |
| Context | OpenStreetMap places | `osmnx` | Register | The destinations for walking access | No |
| Context | MTA subway entrances | NYS `i9wp-a4ja` | Reference | Walking minutes to the nearest subway entrance | No |
| Context | Neighborhoods (2020 NTAs) and Census ACS 5-year estimates by tract | NYC `9nt8-h7nd`, Census API | Reference: the newest release | The neighborhood name, and its income, rent and population | No |
| Context | Building footprints | NYC `5zhs-2jue` | Register | Building height | No |

FAR is floor area ratio: the floor area that a lot can hold, as a multiple of its lot area.

### How v0 fetches the data

- **NYC and NYS Open Data:** the Socrata API. `pull.py` pages through each source, 50,000 rows at a time, in a stable order, and sends the app token from `.env`. The subway entrances are on NYS Open Data, so `pull.py` needs a host for each source.
- **OpenStreetMap:** `osmnx` downloads the walking network and the places for the five boroughs.
- **Census:** the ACS 5-year API, by tract, with `CENSUS_API_KEY` from `.env`.
- **NYC GeoSearch:** turns an address into a BBL, with no key. Accept a match only when it has a BBL.

## The site card

The site card holds the facts about one site, in fixed sections. The `get_site_card` tool returns it.
Every field carries its source dataset and pull date.

| Section | Contents | Source |
|---|---|---|
| Identity | Address, BBL, borough, neighborhood, owner name as recorded | PLUTO, NTAs |
| The lot | Lot area, frontage, depth, land use, building class | PLUTO |
| The building | Floors, units, gross floor area, year built, height | PLUTO, footprints |
| Zoning | Zoning districts, overlays, special districts, maximum FAR by use, built FAR, unused floor area, MIH, transit zone | PLUTO |
| Restrictions | Landmark, historic district, E-designation | PLUTO |
| Price | Last market sale and its price per square foot, the city's market value | Rolling sales, property valuation |
| Activity | New-building and demolition filings on the lot since the start date | DOB NOW job filings |
| Condition | Open vacate orders | HPD vacate orders |
| Neighborhood | Walking minutes to the subway, destinations within a 15-minute walk, the Census profile, density and use mix | OpenStreetMap, MTA, ACS, PLUTO |
| Hazard | FEMA flood flags | PLUTO |

## Urban form in v0

Urban form is a ladder of nine levels of measures of what a place is like, from simple to complex. v0 takes four of them (D9).

| Level | Measures in v0 | Grain |
|---|---|---|
| 1. Lot and building basics | Built FAR, building age, floors, lot coverage, homes per acre | Lot |
| 2. Building geometry | Roof height only | Lot |
| 3. Density and use mix | Homes and floor area per acre, the split of floor area by use, use mix | Neighborhood (NTA) |
| 5. Walking access | Walking minutes to the nearest subway entrance, and the destinations of each kind within a 15-minute walk | Lot |

The use mix uses PLUTO's 11 land-use categories, unchanged.

The destinations for walking access come from OpenStreetMap:

- grocery stores
- schools
- parks
- pharmacies
- shops and retail
- cultural destinations: museums, galleries, theaters and libraries
- other points of interest, such as restaurants and cafes

Notebook `03` sets the OpenStreetMap tags for each kind.
[`ROADMAP.md`](../ROADMAP.md) lists levels 4 and 6 to 9.

## Agents and tools

v0 is an agent harness (D12). Code runs a tool loop: the agent asks for a tool, code runs it, and code sends the result back until the agent gives its verdict.
Every agent gets the same tools, the same data and the same instructions.

The starting tools:

| Tool | Input | Returns |
|---|---|---|
| `lookup_address` | Free text | The matched address and BBL |
| `get_site_card` | BBL | The site card |
| `get_policy` | Developer type | The policy's clauses, its two limits and the risk points |
| `comparable_sales` | BBL, months back | Up to 20 market sales of the same building class in the same neighborhood, with price per square foot |
| `walking_access` | BBL | Walking minutes to the subway, and the count of each destination kind within a 15-minute walk |
| `neighborhood_profile` | BBL | The neighborhood name, its Census profile, and its density and use mix |

No tool writes, sends or deletes.

Write the tool loop by hand first, so that every step is visible:

1. Send the instructions, the tool list and the task: one site and one developer type.
2. If the agent asks for tools, run each one. Send all the results back in one message.
3. If a tool fails, send the failure back as an error result. Do not stop the loop.
4. Repeat until the agent gives its verdict.
5. Stop with an error after 10 rounds.

## The verdict record

Notebook `05` stores one record for each site, developer type and agent.

| Field | Contents |
|---|---|
| `bbl`, `address` | The site |
| `developer_type`, `policy_version` | The policy, and which version of it |
| `model`, `effort`, `prompt_version` | The agent |
| `code_verdict` | Buy, Review or Pass from code |
| `verdict` | Buy, Review or Pass from the agent |
| `clauses` | Each clause the agent cites, with its evidence |
| `letter` | The decision letter |
| `tool_calls` | Each tool call, with its input, in order |
| `tokens`, `cost_usd`, `seconds` | What the verdict cost |

## Comparing agents

Notebook `06` checks each agent's records.

| Check | Question |
|---|---|
| Verdict | Does the verdict match the answer key? |
| Numbers | Does every number in the letter appear in a tool result? |
| Citations | Does each reason cite a clause and a field from the site card? |
| Schema | Does the record have every field, with the right type? |
| Tool use | Which tools did the agent call, and how many times? |
| Cost | Tokens, cost and time for each verdict |

After each run, read ten verdicts. Mark each one right, wrong or unclear, with a note.
Each wrong verdict becomes a test case: the site, the policy and the right verdict.

## How v0 is built

Each step goes through the same three stages (D17).

1. **Explore.** A notebook looks at the data the way a data scientist does exploratory analysis: sizes, columns, missing values, odd values, and how the sources join.
2. **Build.** Code that works in the notebook moves into a module in `src/meridian_dashboard_nyc/`, with tests on a few real rows.
3. **Show.** The notebook imports the module and shows the result.

| Step | Notebook | Module (planned names) | Exists |
|---|---|---|---|
| Look at each source on its own | `01_look_at_each_source` | — | Yes |
| Build the site card for one lot from the five core sources | `02` | `site_card.py` | No |
| Add the context and the urban form: walking network, destinations, subway, neighborhood, footprints | `03` | `context.py` | No |
| Run the three policies over every site, with one code verdict column for each developer type | `04` | `policies.py`, `risk.py` | No |
| The harness: the tools, the tool loop, and each agent's verdicts for a set of sites | `05` | `tools.py`, `harness.py` | No |
| Compare the agents with each other and with the code verdict | `06` | `compare.py` | No |

## Open decisions

These decisions belong to the owner.

1. **The answer key.** When an agent is graded, what is the right verdict: the code verdict, the owner's own verdicts on a set of sites, or both?
2. **What an agent sees.** Is there a tool that returns the code verdict, or does an agent judge without it?
